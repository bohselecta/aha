# AHA constrained scenario engine
## Input and execution
Run input is interval, accepted anchor versions, optional soft premises, explicit exclusions, active contradictions, full relevant retirement ledger, requested count 1–10 and enabled generation families. Freeze the case revision and source text in a snapshot manifest. User sees exactly what is fixed and what may vary. An interval may be open-ended; do not force an alleged crime as a true endpoint unless a human has selected its source-backed proposition.

Preflight validates anchors, temporal satisfiability, scope, provider availability, privacy policy and token budget. Retrieve support AND counter-support through dependency expansion, not only semantic nearest neighbors. Display omitted documents and coverage limits. Generation cannot claim to have reviewed the entire case when only a subset fits. Mandatory anchors/tombstones must fit; otherwise partition the task or stop with a bounded-context error.

Families: minimal assumptions, chronology error in a soft source, interpretation error, unknown actor, independent events mistakenly linked, opportunistic sequence, alternate ordering, conservative conventional explanation, adversarial challenge, and wildcard. Families are prompts for diversity, not ten required labels pasted onto the same story. Wildcard still obeys hard anchors. No invented named person. Known entities may appear only in source-backed roles already represented by selected evidence; unsupported roles use UNKNOWN_ACTOR placeholders. In particular, weak patterns never justify naming a person as an offender.

Model returns schema-constrained scenarios, with each step either referencing an accepted event/observation version or a synthetic step bearing assumptions. Validator checks references, citations, anchor preservation, temporal constraints, prohibited attribution, retirement collisions and output shape. Any hard conflict rejects that scenario. Unsupported free-text claims are held for human review; structured checks cannot fully certify semantic truth. At most one schema-repair attempt and one diversity regeneration per run; show partial results if fewer than requested pass. Never fill to ten by paraphrasing.

## Material distinctness
Represent each scenario with structured `mechanism`, `ordering`, `actor_structure`, `relaxed_premise_ids`, and `independence_assumptions`. Two scenarios are materially distinct only if at least one causal/ordering/actor-structure/independence choice changes and the change yields at least one different discriminating outcome. Wording or place-name changes do not count. Deterministic signature equality rejects duplicates; semantic comparison flags possible duplicates for review. A human can merge duplicates; retain the original run output and decision.

## What to show
Synthetic badge on each scenario and invented step; concise summary, source-linked anchors, assumptions, counter-evidence, unresolved conflicts, unsupported gaps and Questions Worth Checking. Comparison columns are counts/sets: referenced selected observations / selected observations, unique assumptions, unresolved soft conflicts, dependencies on excluded/uncertain premises and discriminating questions. “Referenced” is mechanical, not a claim that the scenario explains the evidence. No weighted total, likelihood, probability, plausibility ranking or winner. Sort only by explicit mechanical fields, with default stable generation-family order.

Each question specifies which scenarios it distinguishes, what different outcomes would imply, possible source to check and limitations. “Check camera synchronization” can separate timing-error versus separate-vehicle pathways. Rank questions by number of distinct outcome partitions, then human-entered effort band; call this separation count, never expected information gain without probabilities. Questions that merely repeat “investigate more” fail validation.

Save to hypothesis requires explicit human review, editable claim, premises and a weakening condition. It creates PROPOSED + SPECULATIVE, never evidence. Re-running is a new ModelRun; old outputs remain viewable with their original provider, schema, prompt, sampling parameters and snapshot. Same model settings do not guarantee byte-identical generation; fixture replay provides reproducible tests.
