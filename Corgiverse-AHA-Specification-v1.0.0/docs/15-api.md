# API behavior
OpenAPI 3.1 lives in `api/openapi.json`. All endpoints begin `/api/v1`; all case access is scoped by UUID and actor. Content is JSON except multipart uploads and authorized file downloads. Domain request/response types reference the bundled schema. Expose no raw SQL, arbitrary file path, generic graph-write or model-tool execution endpoint.

Response headers include X-Request-ID; case reads include ETag containing case revision and X-Index-Revision. Mutation headers require If-Match (quoted case revision) and Idempotency-Key, except initial case creation/import and session bootstrap. Missing precondition is 428, stale revision 409. Authorize before checking object existence; inaccessible records return 404 consistently. Error envelope: code, message, request_id, field_errors and retryable; no stack traces or source text in generic errors.

Status conventions: 201 created; 202 durable job; 200 completed read/command; 204 logout; 400 malformed; 401 no session; 403 policy violation; 404 not visible; 409 conflict; 413 limits; 422 semantic invalidity; 428 missing precondition; 429 bounded queue; 503 unavailable dependency. Paginated lists use stable opaque cursor containing snapshot revision and sort key, limit default 50/max 200. Stale pagination returns 409, not silent duplicate/missing records.

`commands` is a discriminated union, not a generic PATCH: proposeRecord, reviewProposal, transitionHypothesis, reopenHypothesis, decideContradiction, setAnchor, excludeSource. Each has specific authority/semantic rules. proposeRecord stores a pending candidate; reviewer acceptance alone creates an accepted record. Review cannot accept a record based on nonexistent/stale references. No command changes original bytes. New typed command requires schema, tests and documented migration implications.

proposeRecord takes HumanRecordDraft, not a server Record. The service assigns ID, creator, timestamps, scope, revision and PENDING review state; a new hypothesis starts PROPOSED with no predecessor/retirement data. Source-bound human notes/observations use HUMAN origin. Drafts for unsupported record kinds are rejected: Evidence/Derivative come from ingest; ModelRun/Scenario from validated jobs; ReviewAction/CustodyEvent from service events; Contradiction from candidate scan; Anchor and lifecycle changes from explicit commands. Editing an existing accepted proposition requires a new version proposal with a target reference through a separately validated revision command, never replacement of original bytes.

reviseRecord implements that revision command: target must equal current version and draft kind must match; it creates a pending replacement preserving the old accepted version until review. Hypothesis revisions preserve lifecycle and cannot bypass retirement; changing a retired claim requires reopenHypothesis. proposeContradiction also allows a human to submit a sourced candidate without waiting for a scan. answerQuestion creates an audited new question version; ANSWERED requires accepted answer_refs, and CLOSED requires a reason even if unanswered. These commands obey the same revision/idempotency checks.

Lens compile is a 202 job if using a model; execute is deterministic POST with an existing validated plan and returns a view result, never case mutation. Both can run against a pinned revision. Source download takes evidence UUID, not filesystem path. Derivative preview uses its own UUID and content authorization. SSE events include monotonically increasing job event ID, state, progress phase and optional fraction; raw model tokens are not published as validated result.

Uploads require form file + receipt metadata, stream to bounded storage and return ingest job. Portable case import is a distinct route; it cannot overwrite an existing case with same UUID automatically. Export requires section list, format, include_synthetic and redaction plan ID if present. A run can be cancelled without cancelling other users' jobs unless actor is authorized. All model tasks expose validated result and rejection/partial counts.

API contract extensions for agency identity, evidence stores and CASEMAIL are versioned adapters. Service tokens have explicit case scopes and cannot accept evidence tiers or send email. Core browser API and agency import API obey the same validators.

Provider configuration is custodian-only and exposes secret references, never secret values. CasePolicy independently permits or denies remote providers; enabling a provider globally cannot override the case boundary. Endpoint validation must reject unexpected redirects and validate resolved addresses against configured destinations. Job result endpoint returns only the declared result union; pending/failed jobs return a typed 409/422 error. SSE serializes JobEvent under `data:` with `id:` equal to event_id. Saved-view creation/update uses view_revision for conflict checking, not an evidentiary mutation. Technical endpoints still require session/CSRF, authorization and audit where sensitive.
